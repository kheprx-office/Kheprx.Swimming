Base Frontend — Error Handling & Result

The single error contract end to end: how every failure becomes a typed Result that callers switch on — no scattered try/catch.

Result<T> — the uniform return type

Result<T>

domainsrc/app/core/domain/result/result.ts

Every use case returns a Result<T> — a discriminated union with two shapes. The ok boolean acts as a discriminant: TypeScript narrows the type in each branch, so there is no casting and no unchecked property access.

export type Result<T> =
  | { ok: true; data: T }
  | { ok: false; error: AppError };

export const ok = <T>(data: T): Result<T> => ({ ok: true, data });
export const fail = (error: AppError): Result<never> => ({ ok: false, error });

Callers switch on result.ok instead of writing their own try/catch. When ok is true, TypeScript knows result.data is T; when false, it knows result.error is AppError — the union narrows automatically.

AppError and its kinds

AppError

datasrc/app/core/domain/errors/app-error.ts

AppError is the only error type that crosses layer boundaries. Every failure — network, HTTP, validation, storage, crypto — is mapped to an AppError before it reaches the viewmodel, giving the UI a single uniform type to handle.

export type AppErrorKind =
  | 'network' | 'http' | 'validation'
  | 'storage' | 'crypto' | 'auth' | 'unknown';

export class AppError extends Error {
  readonly kind:    AppErrorKind;
  readonly status?: number;
  readonly code?:   string;
  constructor(message: string, kind: AppErrorKind, status?: number, code?: string) {
    super(message);
    this.name = 'AppError';
    this.kind = kind;
    this.status = status;
    this.code = code;
  }
}

The kind field tells the UI what category of failure occurred without leaking implementation details. The optional status carries the HTTP status code; the optional code carries a backend error-code string parsed from the response body — both are set by http-error.ts when the server returns a JSON error body with { message?, code? }.

KindOrigin
'network' http-error.ts — transport failure (status 0) or timeout
'http' http-error.ts — non-2xx (not 401) response; carries status and optional code
'auth' http-error.ts — HTTP 401 response (toAppError maps 401 → 'auth'), e.g. the Identity backend rejecting invalid login credentials
'validation' a use case — bad DTO payload (e.g. ListUsersUseCase when isUserDtoRsValid fails)
'storage' key-value.store.ts — corrupt stored object
'crypto' crypto.service.ts — decrypt/tamper failure
'unknown' UseCase.run() — any non-AppError throw, normalised

See HTTP Client for the full toAppError mapping from HttpErrorResponse to these kinds.

The UseCase base owns the single try/catch

UseCase<I, O>

coresrc/app/core/domain/usecase/use-case.ts

The abstract base uses the template-method pattern: subclasses implement only execute() (the happy path, throws an AppError on failure). run() wraps every call in a single try/catch and normalizes the result, so no use case repeats the same boilerplate.

export abstract class UseCase<I, O> {
  protected readonly log: Logger;
  constructor(name: string) { this.log = createLogger('usecase', name); }

  // happy path only — throw an AppError to signal failure
  protected abstract execute(input: I): Promise<O>;

  async run(input: I): Promise<Result<O>> {
    try {
      return ok(await this.execute(input));
    } catch (e) {
      const error =
        e instanceof AppError ? e : new AppError('Unexpected error', 'unknown');
      return fail(error);
    }
  }
}

Template-method split: subclasses write only execute() — the happy path — and throw an AppError on failure. run() normalizes every throw into a Result exactly once. Any non-AppError exception is wrapped as 'unknown', so the rest of the app only ever sees typed AppError values.

Note: the two this.log.* calls present in the source are omitted here for brevity; all logic is shown.

The rule: no try/catch above run()

Viewmodel consumes Result

presentationsrc/app/features/user-management/presentation/pages/user-management/users.viewmodel.ts

The viewmodel awaits run() and switches on r.ok. There is no try/catch here — the base already normalized every error into a typed value. On success the users signal is updated; on failure the error message is surfaced via NotificationService — the ViewModel does not maintain a separate error signal.

async load(): Promise<void> {
  this.loading.set(true);
  const r = await this.listUsers.run();
  this.loading.set(false);
  if (r.ok) this.users.set(r.data);
  else this.notify.error(r.error.message);
}

Switching on r.ok is the only pattern needed across the entire presentation layer. The viewmodel exposes signals (loading, users) that the template binds to directly — no manual subscriptions, no error propagation, no try/catch. Transient failures are delivered to the user as toast notifications via NotificationService.
