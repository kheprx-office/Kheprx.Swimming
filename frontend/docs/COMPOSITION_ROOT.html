Base Frontend — Composition Root & DI

How the app boots and how every dependency is wired — the Angular counterpart of the mobile base's RootProviders.

How the app boots

Angular's standalone bootstrap wires providers at two levels: global (app-wide in app.config.ts — repository impls, the auth interceptor, and framework services) and route-scoped (ViewModels only, in the route's providers array).

  1. src/main.ts — entry point Calls bootstrapApplication with the root component and the global provider config. 
    bootstrapApplication(App, appConfig)
  .catch((err) => console.error(err));
  2. src/app/app.config.ts — the composition root (global providers) Registers framework-level services and binds all repository tokens to their implementations globally. This is the web equivalent of providers/RootProviders.tsx in the mobile base. 
    export const appConfig: ApplicationConfig = {
  providers: [
    provideBrowserGlobalErrorListeners(),
    provideZoneChangeDetection({ eventCoalescing: true }),
    provideRouter(routes),
    provideHttpClient(withInterceptors([authInterceptor])),
    provideAnimations(),
    ...AUTH_PROVIDERS,
    ...USERS_PROVIDERS,
  ],
};
  3. src/app/app.routes.ts — the route table Maps URL paths to lazy-loaded page components and attaches ViewModel providers scoped to each route's lifetime. See the "Repository bindings" section below for the full route table.
  4. src/app/app.ts — the root shell A minimal standalone component: renders the active route via <router-outlet> and mounts the app-wide notification overlay. 
    @Component({
  selector: 'app-root',
  imports: [RouterOutlet, NotificationHostComponent],
  template: `
    <router-outlet />
    <app-notification-host />
  `,
})
export class App {}

Ports are DI tokens

Why InjectionToken, not an interface?

core pattern

TypeScript interfaces are erased at runtime — Angular's injector cannot use them as keys. Each I…Repository is therefore paired with a matching InjectionToken that survives compilation and acts as the DI key.

Real example from features/user-management/domain/repositories/users.repository.ts:

export interface IUsersRepository {
  list(): Promise<UsersDtoRs>;
  create(rq: CreateUserDtoRq): Promise<UserItemDtoRs>;
  update(id: string, rq: UpdateUserDtoRq): Promise<UserItemDtoRs>;
  setStatus(id: string, rq: SetUserStatusDtoRq): Promise<UserItemDtoRs>;
}

// DI token for the port (interfaces don't exist at runtime).
export const USERS_REPOSITORY = new InjectionToken<IUsersRepository>('USERS_REPOSITORY');

The interface defines the contract; the token is what you actually inject(USERS_REPOSITORY) inside a use case.

Repository bindings: global — ViewModels: route-scoped

Global: repository token → impl in app.config.ts

DI

Repository token→impl bindings are registered globally via spread arrays in app.config.ts. Each feature exports a XXX_PROVIDERS array that maps the token to its implementation; use cases and XxxRepositoryImpl classes are @Injectable({ providedIn: 'root' }).

// data/users.providers.ts
export const USERS_PROVIDERS: Provider[] = [{ provide: USERS_REPOSITORY, useClass: UsersRepositoryImpl }];

// app.config.ts (excerpt)
providers: [
  provideRouter(routes),
  provideHttpClient(withInterceptors([authInterceptor])),
  provideAnimations(),
  ...AUTH_PROVIDERS,
  ...USERS_PROVIDERS,
],

The authInterceptor attaches the Bearer token on every request and retries once on 401 after refreshing the session (bypassing /api/auth/login, /refresh, and /logout).

Route-scoped: ViewModels only

presentation

Only ViewModels are route-scoped — listed in each route's providers array so their lifetime matches the page (created on activate, destroyed on deactivate). The real app.routes.ts:

export const routes: Routes = [
  { path: 'login', loadComponent: () => import('@features/auth').then((m) => m.LoginPage), providers: [LoginViewModel] },
  {
    path: '', component: LayoutComponent, canActivate: [authGuard],
    children: [
      { path: 'home', loadComponent: () => import('@features/home').then((m) => m.HomePage) },
      { path: 'account', loadComponent: () => import('@features/auth').then((m) => m.AccountPage) },
      { path: 'change-password', loadComponent: () => import('@features/auth').then((m) => m.ChangePasswordPage), providers: [ChangePasswordViewModel] },
      { path: 'user-management', canActivate: [roleGuard('admin')], loadComponent: () => import('@features/user-management').then((m) => m.UserManagementPage), providers: [UsersViewModel] },
      { path: '', pathMatch: 'full', redirectTo: 'home' },
    ],
  },
  { path: '**', redirectTo: '' },
];

LoginViewModel, ChangePasswordViewModel, and UsersViewModel are created when their route activates and destroyed when it deactivates. roleGuard('admin') restricts user-management to admin users; authGuard protects all children of the LayoutComponent shell.
