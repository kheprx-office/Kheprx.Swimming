Base Frontend — Testing

How testing is set up, what each layer's spec covers, and the TestBed recipes for use cases and viewmodels.

Where specs live — the testing/ folder

Every *.spec.ts file lives inside the feature's testing/ folder, which mirrors the source tree down to the screen folder. No spec file lives next to its source file.

features/<feature>/
  data/                                      # source only — no specs here
  domain/                                    # source only — no specs here
  presentation/                              # source only — no specs here
  testing/                                   # all *.spec.ts live here
    data/
      dto/<entity>.dto.spec.ts
      repositories/<entity>.repository.impl.spec.ts
    domain/
      usecases/<verb>-<entity>.use-case.spec.ts
    presentation/
      <non-page>.spec.ts                     # e.g. auth-session.store.spec.ts, auth.guard.spec.ts
      pages/
        <screen>/
          <screen>.viewmodel.spec.ts         # or <screen>.page.spec.ts for smoke tests

Two rules:

  1. Mirror the source path. The path inside testing/ matches the corresponding source path down to the screen folder (e.g. a spec for presentation/pages/user-management/users.viewmodel.ts lives at testing/presentation/pages/user-management/users.viewmodel.spec.ts).
  2. Import via aliases, not relative paths. Specs import the unit under test using @features/… or @core/… path aliases — never a relative ../… import from inside testing/. The moduleNameMapper in jest.config.js resolves aliases identically to the compiler.

Jest discovers all specs automatically via its **/*.spec.ts glob — no Jest config change is needed when adding new spec files inside testing/.

Setup

jest-preset-angular

core

Tests run with Jest via jest-preset-angular. The CommonJS preset handles the Angular compiler transform; setup-jest.ts initialises the zone environment for each test run. Run the full suite with npm test.

// jest.config.js
const { createCjsPreset } = require('jest-preset-angular/presets');

module.exports = {
  ...createCjsPreset(),
  setupFilesAfterEnv: ['<rootDir>/setup-jest.ts'],
  moduleNameMapper: {
    '^@core/(.*)$': '<rootDir>/src/app/core/$1',
    '^@features/(.*)$': '<rootDir>/src/app/features/$1',
  },
};
// setup-jest.ts
import { setupZoneTestEnv } from 'jest-preset-angular/setup-env/zone';

setupZoneTestEnv();

The moduleNameMapper path aliases mirror tsconfig.json so import paths are resolved identically in tests and in the compiler.

Coverage

One spec file per testable unit. Component-level tests are deliberately light smoke tests — matching the pragmatic depth of the mobile base.

Spec file What the tests verify
result.spec.ts ok() and fail() constructors; type narrowing via .ok.
use-case.spec.ts Success path returns ok(data); thrown AppError returns fail(error) with correct kind; non-AppError normalised to 'unknown'.
app-error.spec.ts AppError constructor sets kind and message; instanceof check distinguishes it from a plain Error.
logger.spec.ts Logger does not throw; levels propagate correctly.
http-client.spec.ts Transport failure → AppError('network'); non-2xx → AppError('http', status); timeout maps to network; retry count is respected. Uses HttpClientTestingModule.
key-value.store.spec.ts Round-trip set/get; missing key returns null / fallback; corrupt object throws AppError('storage'); corrupt primitive falls back silently.
crypto.service.spec.ts Encrypt → decrypt round-trip; tampered ciphertext throws AppError('crypto'). Uses Node's webcrypto and an in-memory KeyProvider.
nav-button.component.spec.ts Renders label; emits press on click; disabled state prevents emit.
text-field.component.spec.ts Renders the label binding; emits valueChange on user input, updating the parent signal.
decor-background.component.spec.ts Smoke test: decorative background component renders without error.
notification.service.spec.ts success() / error() enqueue the correct notification type.
app.routes.spec.ts Route configuration is valid; login is public; protected routes require authGuard; user-management additionally requires roleGuard('admin').
layout.component.spec.ts Layout shell renders the <router-outlet> and navigation; smoke test.
session.dto.spec.ts isSessionDtoRsValid passes on a complete session DTO; rejects empty tokens, unknown role, or non-boolean mustChangePassword.
current-user.dto.spec.ts isCurrentUserDtoRsValid passes on a complete current-user DTO; rejects empty userId or unknown role.
auth.spec.ts toAuthSession, toAuthTokens, and toAuthPrincipal map DTO shapes to the correct domain model fields.
auth.repository.impl.spec.ts Each method delegates to the correct /api/auth/… endpoint and returns the raw envelope; uses HttpClientTestingModule.
token-store.spec.ts Round-trip store/retrieve of access and refresh tokens; missing token returns null; clear removes both.
login.use-case.spec.ts Valid credentials return ok(AuthSession); invalid DTO response causes fail('validation').
refresh-token.use-case.spec.ts No stored refresh token → fail('auth') (status 401); valid response → validates + maps to AuthTokens and persists them in TokenStore; malformed session DTO (e.g. empty accessToken) → fail('validation').
logout.use-case.spec.ts Calls the logout endpoint; token store is cleared on success.
change-password.use-case.spec.ts Valid password change returns ok; HTTP failure propagates as fail.
load-current-user.use-case.spec.ts Valid current-user DTO → mapped to AuthPrincipal; malformed DTO (e.g. unknown role) → fail('validation').
auth-session.store.spec.ts Rehydrates session on init via LoadCurrentUserUseCase; session signal updates on login; clears on logout.
auth.guard.spec.ts authGuard redirects to /login when unauthenticated; roleGuard('admin') blocks users without the admin role.
auth.interceptor.spec.ts Attaches Bearer token to outgoing requests; intercepts 401, refreshes token, and retries; bypasses /api/auth/login, /refresh, and /logout.
login.viewmodel.spec.ts Login success populates the session signal and clears the error; failure sets the error signal and leaves session null.
change-password.viewmodel.spec.ts Success clears the error signal; failure sets it with the correct message.
user.dto.spec.ts isUserDtoRsValid passes on a valid DTO; rejects unknown role, invalid status, empty id, or non-boolean mustChangePassword.
user.spec.ts toUser maps a valid UserDtoRs to a User domain model with correct field types.
users.repository.impl.spec.ts list, create, update, and setStatus delegate to the correct /api/users/… endpoints; uses HttpClientTestingModule.
users.use-cases.spec.ts ListUsersUseCase maps valid DTOs to User[]; invalid DTO row → fail('validation'). Fake USERS_REPOSITORY injected via token.
users.viewmodel.spec.ts Success populates the users signal; failure calls notify.error(...) (NotificationService); create/update/setStatus success refreshes the user list.
home.page.spec.ts Home page renders navigation links.

Use-case test recipe

Bind a fake repository to the port token

domain

The use case depends on USERS_REPOSITORY (an InjectionToken), so tests swap the real implementation for a minimal in-memory fake — no HTTP, no Angular HTTP testing module needed.

import { TestBed } from '@angular/core/testing';
import { ListUsersUseCase } from '@features/user-management/domain/usecases/user-management/list-users.use-case';
import { USERS_REPOSITORY, IUsersRepository } from '@features/user-management/domain/repositories/users.repository';
import { UserDtoRs } from '@features/user-management/data/dto/user-management/user.dto';

const dto: UserDtoRs = { id: 'USR-1', fullName: 'A', email: 'a@b.c',
  role: 'worker', status: 'active', mustChangePassword: false };

function repo(overrides: Partial<IUsersRepository> = {}): IUsersRepository {
  return { list: async () => ({ data: [dto] }), ...overrides } as IUsersRepository;
}

TestBed.configureTestingModule({
  providers: [{ provide: USERS_REPOSITORY, useValue: repo() }],
});
const uc = TestBed.inject(ListUsersUseCase);
const r = await uc.run();
// use case validates each DTO with isUserDtoRsValid, then maps via toUser
expect(r.ok).toBe(true);
if (r.ok) expect(r.data).toEqual([{ id: 'USR-1', fullName: 'A', email: 'a@b.c',
  role: 'worker', status: 'active', mustChangePassword: false }]);

The second case overrides list to return a DTO row with an invalid status value. The use case's isUserDtoRsValid guard rejects it and toUser is never called, causing r.ok === false with r.error.kind === 'validation'. No try/catch is needed in the test — UseCase.run() normalises all thrown errors into a typed Result.

ViewModel test recipe

Stub all use cases and assert on signal transitions

presentation

The viewmodel injects four use cases plus NotificationService. Tests replace all of them with stubs, set list.run to resolve ok([user]), then assert on signal values after calling vm.load(). All four use-case stubs must be provided or Angular's DI will throw.

import { TestBed } from '@angular/core/testing';
import { UsersViewModel } from '@features/user-management/presentation/pages/user-management/users.viewmodel';
import { ListUsersUseCase }     from '@features/user-management/domain/usecases/user-management/list-users.use-case';
import { CreateUserUseCase }    from '@features/user-management/domain/usecases/user-management/create-user.use-case';
import { UpdateUserUseCase }    from '@features/user-management/domain/usecases/user-management/update-user.use-case';
import { SetUserStatusUseCase } from '@features/user-management/domain/usecases/user-management/set-user-status.use-case';
import { NotificationService }  from '@core/ui/notification.service';
import { ok } from '@core/domain/result/result';
import { User } from '@features/user-management/domain/model/user-management/user';

const user: User = { id: 'USR-1', fullName: 'A', email: 'a@b.c',
  role: 'worker', status: 'active', mustChangePassword: false };

const list      = { run: jest.fn().mockResolvedValue(ok([user])) };
const create    = { run: jest.fn() };
const update    = { run: jest.fn() };
const setStatus = { run: jest.fn() };
const notify    = { success: jest.fn(), error: jest.fn() };

TestBed.configureTestingModule({
  providers: [
    UsersViewModel,
    { provide: ListUsersUseCase,     useValue: list },
    { provide: CreateUserUseCase,    useValue: create },
    { provide: UpdateUserUseCase,    useValue: update },
    { provide: SetUserStatusUseCase, useValue: setStatus },
    { provide: NotificationService,  useValue: notify },
  ],
});
const vm = TestBed.inject(UsersViewModel);
await vm.load();
expect(vm.loading()).toBe(false);
expect(vm.users()).toHaveLength(1);

Additional cases override create.run / setStatus.run with a resolved fail(…) to confirm the viewmodel surfaces the error message via notify.error() and keeps the modal open — the signals are never inconsistent.

Component tests (nav-button.component.spec.ts, decor-background.component.spec.ts, etc.) are light smoke tests that confirm rendering and basic interaction — matching the pragmatic depth of the mobile base.
