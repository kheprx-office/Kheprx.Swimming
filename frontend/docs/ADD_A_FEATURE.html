Base Frontend — Add a Feature

Add a vertical slice by following the user-management / User example. Substitute your entity name wherever User/user appears.

Folder scaffold

Create this directory tree under src/app/features/, substituting your feature name and entity name for the placeholders.

src/app/features/<feature>/
  data/
    dto/
      <screen>/            ← <resource>.dto.ts  (response DTOs + envelopes + isValid guard) · one file per request DTO
      shared/              ← when DTO is used by the store/interceptor/app-init or across screens
    repositories/          ← <entity>.repository.impl.ts  (<Entity>RepositoryImpl)
    <feature>.providers.ts ← XXX_PROVIDERS: bind token → impl
  domain/
    model/
      <screen>/            ← <entity>.ts  (screen-specific input types)
      shared/              ← <aggregate>.ts  (feature-wide model + mappers)
    repositories/          ← <entity>.repository.ts  (I<Entity>Repository port + DI token)
    usecases/
      <screen>/            ← <verb>-<entity>.use-case.ts  (owned by the triggering screen)
      shared/              ← when use case is owned by store/interceptor/app-init or is multi-screen
  presentation/
    pages/
      <screen>/            ← <screen>.page.ts · <screen>.page.html · <screen>.viewmodel.ts (if any)
    ← non-screen files (stores, guards) at presentation/ root
  testing/                 ← mirrors data/ · domain/ · presentation/ — all *.spec.ts live here
  index.ts                 ← public barrel

The 11-step recipe

  1. DTO + validator — data/dto/user-management/user.dto.ts

    Response DTOs and their validator live together in one file under the screen subfolder (e.g. data/dto/user-management/user.dto.ts). Each request DTO gets its own file (e.g. data/dto/user-management/create-user.dto.ts). Use shared/ when the DTO is consumed by the store, interceptor, app-init, or multiple screens. Response DTOs are suffixed …DtoRs; request DTOs …DtoRq. Envelope types extend BaseResponseRs<T> from core.

    import { BaseResponseRs } from '@core/network/api/base-response-rs';
import { ROLE_LABELS } from '@core/domain/roles';

export interface UserDtoRs {
  id: string; fullName: string; email: string;
  role: string; status: string; mustChangePassword: boolean;
}
export interface UsersDtoRs extends BaseResponseRs<UserDtoRs[]> {}
export interface UserItemDtoRs extends BaseResponseRs<UserDtoRs> {}

export function isUserDtoRsValid(dto: UserDtoRs): boolean {
  return (
    typeof dto.id === 'string' && dto.id.length > 0 &&
    typeof dto.fullName === 'string' &&
    typeof dto.email === 'string' &&
    typeof dto.role === 'string' &&
    Object.prototype.hasOwnProperty.call(ROLE_LABELS, dto.role) &&
    (dto.status === 'active' || dto.status === 'disabled') &&
    typeof dto.mustChangePassword === 'boolean'
  );
}
  2. Domain model + mapper — domain/model/user-management/user.ts

    The clean domain type, free of transport-layer concerns, plus a pure mapper from DTO. The mapper lives alongside the type so the domain/data boundary is clear.

    export type UserStatus = 'active' | 'disabled';
export interface User {
  id: string; fullName: string; email: string;
  role: UserRole; status: UserStatus; mustChangePassword: boolean;
}

export function toUser(dto: UserDtoRs): User {
  return {
    id: dto.id, fullName: dto.fullName, email: dto.email,
    role: dto.role as UserRole, status: dto.status as UserStatus,
    mustChangePassword: dto.mustChangePassword,
  };
}
  3. Port + DI token — domain/repositories/users.repository.ts

    Define the interface (port) and an InjectionToken so the use case depends on an abstraction, not an implementation. Interfaces vanish at runtime; the token gives Angular something concrete to bind. The port methods return the raw DTO envelope — mapping is the use case's responsibility.

    export interface IUsersRepository {
  list(): Promise<UsersDtoRs>;
  create(rq: CreateUserDtoRq): Promise<UserItemDtoRs>;
  update(id: string, rq: UpdateUserDtoRq): Promise<UserItemDtoRs>;
  setStatus(id: string, rq: SetUserStatusDtoRq): Promise<UserItemDtoRs>;
}

export const USERS_REPOSITORY = new InjectionToken<IUsersRepository>('USERS_REPOSITORY');
  4. Repository impl — data/repositories/users.repository.impl.ts

    Injects HttpClientService directly and returns the raw DTO envelope. This is a fetch-only repository — no DTO validation, no domain mapping, no branching logic. Those responsibilities belong to the use case. Mark it providedIn: 'root' so it participates in tree-shaking and is bound globally via the providers file.

    @Injectable({ providedIn: 'root' })
export class UsersRepositoryImpl implements IUsersRepository {
  private readonly http = inject(HttpClientService);

  list(): Promise<UsersDtoRs> {
    return this.http.get<UsersDtoRs>('/api/users');
  }
  create(rq: CreateUserDtoRq): Promise<UserItemDtoRs> {
    return this.http.post<UserItemDtoRs>('/api/users', { body: rq });
  }
  update(id: string, rq: UpdateUserDtoRq): Promise<UserItemDtoRs> {
    return this.http.patch<UserItemDtoRs>(`/api/users/${id}`, { body: rq });
  }
  setStatus(id: string, rq: SetUserStatusDtoRq): Promise<UserItemDtoRs> {
    return this.http.patch<UserItemDtoRs>(`/api/users/${id}/status`, { body: rq });
  }
}

    See Repository Layer for HttpClientService method signatures and error-handling behaviour.

  5. Use case — domain/usecases/user-management/list-users.use-case.ts

    Orchestrates the fetch: calls the port, validates every DTO item with the guard, maps to domain models. Errors thrown here are caught by UseCase.run() and returned as a typed Result — no try/catch needed in callers. Place each use case under the screen subfolder that triggers it; use domain/usecases/shared/ for store-, interceptor-, or app-init-owned use cases, or those shared across multiple screens.

    @Injectable({ providedIn: 'root' })
export class ListUsersUseCase extends UseCase<void, User[]> {
  private readonly repo = inject(USERS_REPOSITORY);

  constructor() { super('ListUsers'); }

  protected async execute(): Promise<User[]> {
    const res = await this.repo.list();
    if (!res.data.every(isUserDtoRsValid)) {
      throw new AppError('Invalid user data received', 'validation');
    }
    return res.data.map(toUser);
  }
}
  6. Screen folder — presentation/pages/user-management/

    Create the screen folder and place the viewmodel inside it alongside the page component and template. Here the viewmodel (users.viewmodel.ts) and page (user-management.page.ts) both live under presentation/pages/user-management/. Non-screen presentation files (stores, guards) stay at the presentation/ root.

    ViewModel — presentation/pages/user-management/users.viewmodel.ts

    Exposes loading and users signals only — no error signal. Calls the use case, then switches on result.ok. On failure, surfaces the error via NotificationService.error(...) — the users list is not cleared. The ViewModel is provided at route level (not globally) so it is instantiated and torn down with the route.

    @Injectable()
export class UsersViewModel {
  private readonly listUsers = inject(ListUsersUseCase);
  private readonly notify = inject(NotificationService);

  readonly loading = signal(false);
  readonly users   = signal<User[]>([]);

  async load(): Promise<void> {
    this.loading.set(true);
    const r = await this.listUsers.run();
    this.loading.set(false);
    if (r.ok) this.users.set(r.data);
    else this.notify.error(r.error.message);   // toast via NotificationService
  }
}
  7. Page — presentation/pages/user-management/user-management.page.ts

    Injects the ViewModel and renders from its signals. Errors are surfaced by the ViewModel itself (via NotificationService) — the Page has no error-handling logic of its own.

    @Component({
  selector: 'app-user-management-page',
  standalone: true,
  imports: [NavButtonComponent],
  template: `
    <section class="page">
      <h1>User Management</h1>
      <app-nav-button label="Refresh" (press)="onLoad()" [disabled]="vm.loading()" />
      @if (vm.loading()) { <p>Loading…</p> }
      @if (vm.users().length) { <p>{{ vm.users().length }} users</p> }
    </section>
  `,
})
export class UserManagementPage {
  readonly vm = inject(UsersViewModel);

  onLoad(): void {
    void this.vm.load();
  }
}
  8. Barrel — index.ts

    The feature's public surface. Only the page and viewmodel are re-exported here. The repository impl, use cases, token, and providers are wired globally via app.config.ts (USERS_PROVIDERS) or provided at route scope — they do not need to appear in the barrel.

    export { UserManagementPage } from './presentation/pages/user-management/user-management.page';
export { UsersViewModel }      from './presentation/pages/user-management/users.viewmodel';
  9. Providers + composition root — data/<feature>.providers.ts + src/app/app.config.ts

    The token→impl binding is declared once in a providers file and spread globally into app.config.ts — not into a route's providers. Use cases and the repository impl are providedIn: 'root'. Only the ViewModel is provided at route level, scoped to that route's lifetime.

    // data/users.providers.ts
export const USERS_PROVIDERS: Provider[] = [
  { provide: USERS_REPOSITORY, useClass: UsersRepositoryImpl },
];

// src/app/app.config.ts (excerpt)
providers: [
  provideRouter(routes),
  provideHttpClient(withInterceptors([authInterceptor])),
  provideAnimations(),
  ...AUTH_PROVIDERS,
  ...USERS_PROVIDERS,
],

    In app.routes.ts, provide only the ViewModel at route level. Add canActivate: [roleGuard('admin')] for admin-only routes:

    {
  path: 'user-management',
  canActivate: [roleGuard('admin')],
  loadComponent: () => import('@features/user-management').then((m) => m.UserManagementPage),
  providers: [UsersViewModel],
},
  10. Tests — use-case and viewmodel

    Place specs under the feature's testing/ folder, mirroring the source path. Domain specs go in testing/domain/usecases/…; a viewmodel spec goes in testing/presentation/pages/<screen>/<screen>.viewmodel.spec.ts. Import the unit under test via @features/@core aliases — no relative imports from within testing/. Jest discovers all *.spec.ts files automatically via its **/*.spec.ts glob; no config change is needed. See Testing for the full TestBed recipes.

  11. Add to nav/home

    Register the route path in any navigation component and add a link to the home page. The Angular router resolves the path entry declared in Step 9; USERS_PROVIDERS in app.config.ts ensures the correct repository implementation is available globally, while UsersViewModel in the route's providers scopes the viewmodel lifetime to the route.

Two repository-port patterns

The return type of the port interface reveals the trust level of the data source and determines whether a DTO layer is needed.

Remote / untrusted

data

The port returns the raw DTO envelope (UsersDtoRs). The use case owns validation and mapping — keeping the repository free of domain logic and keeping the domain free of transport-layer types.

Port signature: list(): Promise<UsersDtoRs>
Pattern: repository fetches → use case validates with guard → use case maps to domain model.

Local / trusted (note): When data originates from your own app (e.g. a KeyValueStore-backed preference store), the port may return a domain model directly — no DTO envelope or guard is needed. The repository serialises and deserialises internally via KeyValueStore. This pattern is not used for API-backed features.

Rule: surface failures via NotificationService. When the use case returns result.ok === false, call this.notify.error(r.error.message). Do not clear the users list — stale data remains visible until the next successful load. No error signal is needed on the ViewModel. 
if (r.ok) this.users.set(r.data);
else this.notify.error(r.error.message);   // toast via NotificationService
