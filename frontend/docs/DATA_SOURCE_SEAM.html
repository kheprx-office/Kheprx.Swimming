Repository Layer

Repositories are fetch-only: they call HttpClientService directly and return the raw DTO envelope. Validation and domain mapping belong to the use case — there is no data-source seam.

The rule: a repository returns BaseResponseRs<T> (the raw server envelope). It does not unwrap .data, validate, or map to a domain model. Those steps live in the use case.

The boundary rule — fetch-only repositories

Data flow

domain

The full data path is: Page → ViewModel (signals) → UseCase.run() → IXxxRepository → XxxRepositoryImpl → HttpClientService. The repository is the network boundary. The use case owns the single try/catch and returns Result<T>.

Inside a use case's execute():

const res = await this.repo.list();                                    // returns UsersDtoRs (the envelope)
if (!res.data.every(isUserDtoRsValid)) throw new AppError('Invalid user data received', 'validation');
return res.data.map(toUser);                                          // maps DTO → domain model

The port + token (domain)

IUsersRepository + USERS_REPOSITORY

domainfeatures/user-management/domain/repositories/users.repository.ts

The interface returns DTO envelopes directly. The injection token is a plain InjectionToken — no interface-level coupling to Angular DI, just a typed key for the provider binding.

export interface IUsersRepository {
  list(): Promise<UsersDtoRs>;
  create(rq: CreateUserDtoRq): Promise<UserItemDtoRs>;
  update(id: string, rq: UpdateUserDtoRq): Promise<UserItemDtoRs>;
  setStatus(id: string, rq: SetUserStatusDtoRq): Promise<UserItemDtoRs>;
}
export const USERS_REPOSITORY = new InjectionToken<IUsersRepository>('USERS_REPOSITORY');

The impl (data)

UsersRepositoryImpl

datafeatures/user-management/data/repositories/users.repository.impl.ts

The implementation injects HttpClientService directly. Every method forwards the call and returns the envelope untouched — no unwrapping, no validation, no mapping. It is @Injectable({ providedIn: 'root' }) so Angular can create it without an extra provider entry.

@Injectable({ providedIn: 'root' })
export class UsersRepositoryImpl implements IUsersRepository {
  private readonly http = inject(HttpClientService);
  list(): Promise<UsersDtoRs> { return this.http.get<UsersDtoRs>('/api/users'); }
  create(rq: CreateUserDtoRq): Promise<UserItemDtoRs> { return this.http.post<UserItemDtoRs>('/api/users', { body: rq }); }
  update(id: string, rq: UpdateUserDtoRq): Promise<UserItemDtoRs> { return this.http.patch<UserItemDtoRs>(`/api/users/${id}`, { body: rq }); }
  setStatus(id: string, rq: SetUserStatusDtoRq): Promise<UserItemDtoRs> { return this.http.patch<UserItemDtoRs>(`/api/users/${id}/status`, { body: rq }); }
}

Wiring — providers and composition root

Token → impl binding

corefeatures/user-management/data/users.providers.ts · src/app/app.config.ts

The token→impl binding is declared in the feature's data/users.providers.ts and spread globally into app.config.ts. Use cases and repository impls are all providedIn: 'root'; only ViewModels are route-scoped (provided in app.routes.ts).

// data/users.providers.ts
export const USERS_PROVIDERS: Provider[] = [{ provide: USERS_REPOSITORY, useClass: UsersRepositoryImpl }];

// app.config.ts (excerpt)
providers: [
  provideRouter(routes),
  provideHttpClient(withInterceptors([authInterceptor])),
  provideAnimations(),
  ...AUTH_PROVIDERS,
  ...USERS_PROVIDERS,
],

Testing the seam

Fake repository via token

core

In a TestBed spec, override the token with a fake implementation. The use case receives the interface it expects; no real HTTP calls are made.

const fakeRepo: IUsersRepository = {
  list: () => Promise.resolve({ data: [], success: true }),
  create: jest.fn(),
  update: jest.fn(),
  setStatus: jest.fn(),
};

TestBed.configureTestingModule({
  providers: [
    { provide: USERS_REPOSITORY, useValue: fakeRepo },
    ListUsersUseCase,
  ],
});

Alternatively, spy on HttpClientService directly when testing the repository impl in isolation — useful for verifying that the correct path and body are sent.
