AD-001 Frontend token storage Decided Frontend 2026-06-30 · gap G1
Decision
localStorage + Bearer header (Option A). Tokens are kept in the existing TokenStore (localStorage-backed KeyValueStore); the access token is sent on the Authorization: Bearer <token> header via authInterceptor; the refresh token is sent in the POST /api/auth/refresh request body. No httpOnly cookies.
Why
Matches what the frontend already implements (no rework); simplest path with no backend contract change; this is an internal ERP with a controlled user base. The XSS exposure of a JS-readable refresh token is mitigated by a short-lived access token and refresh-token rotation + reuse detection.
Affects
/api/auth/refresh & /api/auth/logout keep taking the refresh token in the body (not a cookie); CORS stays header-based (no credentialed cookies); frontend keeps its current TokenStore + interceptor. Security posture depends on G2 (reuse detection) and G10 (short access-token TTL) — both still open.
AD-002 Refresh-token reuse detection Decided Backend 2026-06-30 · gap G2
Decision
Revoke all the user's sessions on reuse (Option C). When a refresh token that has already been rotated/revoked is replayed at /api/auth/refresh (the token is found by hash but is no longer active), treat it as a theft signal and revoke every refresh token for that user, then return 401. The user must sign in again on all devices.
Why
Simplest to build — a single "revoke all for this user" operation, with no token-family tracking / no FamilyId column. Strongest containment: a stolen token cannot outlive detection on any device. Acceptable for an internal ERP where forcing a full re-login on a theft signal is fine.
Detection
/refresh looks up the presented token by hash: active → normal rotate; found but revoked → reuse → revoke all of the user's tokens + 401; expired or not found → plain 401 (no mass revoke).
Affects
No schema change. Refines the /api/auth/refresh logic (the earlier plan returned null on any inactive token; now a revoked token additionally triggers the mass revoke). Pairs with G1.
AD-003 Sessions on password change / reset Decided Backend 2026-06-30 · gap G3 · deferred feature
Decision
Keep current device, revoke the rest (Option C). change-password (authenticated): revoke all of the user's refresh tokens, then issue a fresh token pair for the caller — so the current device stays signed in and every other session drops. reset-password (unauthenticated): revoke all refresh tokens, no reissue — the user signs in fresh.
Why
Standard, good-UX pattern: don't sign the user out of the device they're actively using to change the password, while still killing other (possibly compromised) sessions. Reset has no current session, so revoke everything.
Affects
Applies to the deferred password feature (not in the first build slice). change-password returns a new SessionDto; "keep current" is achieved by revoke-all + reissue-for-caller (no need to identify which stored token is the current one). No schema change.
Superseded
The reset-password half is removed by AD-014 (no email-based recovery). The change-password revoke-all + reissue-for-caller behaviour stands.
AD-004 Login abuse protection Decided · defer Backend 2026-06-30 · gap G4
Decision
Defer — no rate-limiting or account lockout in this build. Protection rests on strong passwords (G11), short-lived access tokens (G10), and refresh-reuse detection (AD-002). Revisit if/when the API is exposed beyond the internal network.
Why
Internal ERP with a controlled user base → lower brute-force risk; keep the first build lean.
Affects
Nothing built now. When added, the simplest option is an IP-based ASP.NET Core rate limiter on /api/auth/login (no schema change); account lockout would need FailedLoginCount / LockedUntil columns.
AD-005 Unified Users identity Decided Architecture 2026-06-30 · gap G5 · reflected in blueprint ✓
Decision
One unified identity.Users (Option A). The auth Users table is the canonical person + login identity the ERP attaches profiles to. Email and PasswordHash are nullable (a login-less person — e.g. a field worker — has neither); login rejects any user with no PasswordHash. The Identity module owns Users + Roles; a later People/HR feature owns the Manager/Moqawel/Worker profiles, which reference Users.Id via the module contract.
Why
Single source of truth for identity; avoids a painful identity split/merge migration later; matches the ERP blueprint's existing Users + profiles design.
Affects
Backend blueprint updated: Users.Email & Users.PasswordHash are now nullable with updated notes (visible in auth-api-blueprint.html). Login flow must reject login-less users. The profiles + extra person fields (Code/Gender/Age/Nid…) come with the future People/HR feature.
AD-006 Build phasing Decided Scope 2026-06-30 · gap G6 · reflected in blueprint ✓
Decision
Phase 1 (first build): Login & Sessions, Refresh & Logout, Roles & Authorization — /api/auth/login,refresh,logout,me + /api/roles, JWT validation, the 4 seeded roles, and a seeded initial admin.
Phase 2 (later): Password Management (forgot/reset/change + email seam) and User Management (/api/users CRUD + role assignment).
Frontend (parallel): Mock→Http switch + role-model 2→4 (G8).
Why
Smallest coherent first slice that delivers working auth end-to-end; an initial seeded admin removes the need for user-management in Phase 1.
Affects
Each feature in auth-api-blueprint.html now carries a [Phase 1] / [Phase 2] tag in its description.
Superseded
AD-014 drops email-based forgot/reset and the email seam from Phase 2; the only password feature is change-password (pulled into Phase 1 by AD-007).
AD-007 Initial accounts & forced first-login change Decided Backend 2026-06-30 · gap G7 · reflected in blueprint ✓
Decision
Seed one fixed account per role (Option B, all four roles): admin@kheprx.local, manager@kheprx.local, moqawel@kheprx.local, worker@kheprx.local — each with a known default password (from the seeder/config), and MustChangePassword = true so the app forces a password change on first login.
Why
Simplest bootstrap — a working account for every role out of the box; force-change-on-first-login closes the default-credential risk. For production, set strong default passwords via config secrets; the forced change rotates them on first sign-in.
Affects
Schema: Users.MustChangePassword (bool, default false; seeded accounts true). SessionDto gains mustChangePassword so login/refresh signal the client to redirect to change-password. Phasing consequence: change-password is pulled into Phase 1 (it's required to satisfy the forced change); forgot/reset removed entirely (AD-014). Updates AD-006.

AD-009Multi-device sessions & logout scope DecidedBackend 2026-06-30 · gap G9 · reflected in blueprint ✓
Decision
A user may be signed in on multiple devices (a new login does not revoke prior sessions). Logout signs out everywhere: POST /api/auth/logout revokes all the caller's refresh tokens (userId from the access token; no request body needed).
Affects
Blueprint logout endpoint updated (was "revoke caller's refresh token", now "revoke ALL … sign out everywhere", req —). Consistent with AD-002/AD-003's "revoke all" stance.
AD-010Token lifetimes DecidedPolicy 2026-06-30 · gap G10
Decision
Access token 15 min; refresh token 7 days, both absolute (the refresh window is not extended on use — 7 days from issue). Config: Jwt:AccessTokenMinutes=15, Jwt:RefreshTokenDays=7. A continuously-active user re-authenticates weekly.
AD-011Password policy DecidedBackend 2026-06-30 · gap G11 · reflected in blueprint ✓
Decision
Minimum length 8, no complexity rules (length over complexity). Applies to password-creation fields (newPassword, temporaryPassword). Login itself enforces no length rule — it validates the submitted password against the stored hash, so existing short passwords still work.
Affects
Blueprint DTO rules updated to MinLength(8) on creation fields; LoginRequest.password is now just NotEmpty.
AD-012CORS policy DecidedBackend 2026-06-30 · gap G12
Decision
Lock CORS to configured origins. Replace the base AllowAll with an allowlist of frontend origins read from config (dev + prod URLs). Because tokens go on the Authorization header (not cookies, per AD-001), the policy does not need AllowCredentials.
AD-013Email-sending seam RetiredBackend 2026-06-30 · gap G13 · retired by AD-014
Decision
Define an IEmailSender abstraction now; pick the concrete provider later. The Phase-2 password-reset (forgot-password) flow depends on it; the actual implementation (SMTP or a provider) is chosen when that feature is built. No provider commitment now.
Retired
Superseded by AD-014. The only consumer was the email-based forgot/reset flow, which is removed. No email-based recovery now or in the future; IEmailSender is not introduced. Kept for audit trail.
AD-014Drop email-based password recovery (forgot / reset) DecidedBackendFrontend Scope 2026-06-30 · client request
Decision
Remove self-service / email-based password recovery entirely. Drop POST /api/auth/forgot-password and POST /api/auth/reset-password, the ForgotPasswordRequest / ResetPasswordRequest DTOs, the identity.PasswordResetTokens table, and the email seam (IEmailSender, AD-013). change-password is kept — it is required to satisfy AD-007 (forced password change on first login).
Why
Client request: no email-based recovery now or in the future. Removing it deletes the only consumer of the email seam, so the seam is retired rather than carried as dead scope. Forced-first-login security is unaffected — change-password + MustChangePassword still cover it.
Affects
Supersedes the reset-password half of AD-003; removes forgot/reset + the email seam from AD-006 Phase 2; updates the phasing note in AD-007; retires AD-013. Blueprint docs (auth-api-blueprint.html, auth-feature-flows.html) updated to match. MustChangePassword, the login → change-password redirect, and AD-011 password policy are unchanged.
