Kheprx.BaseBackend — Architecture Overview

A .NET 10 modular monolith. Read this first, then Solution Structure, Request Flow, and Module Anatomy.

Modular monolith: one deployable host, many self-contained modules. Modules never reference each other's internals — only their .Contracts.
Layers: DomainApplication InfrastructureContracts Host / ApiSharedKernel

Who references whom

Every arrow is a real <ProjectReference> in the .csproj — “X → Y” means X references Y. The host points to one module's Infrastructure; Infrastructure pulls in everything it needs; the inner layers point only inward.

Contracts has no outgoing arrow — it references nothing (its .csproj is empty). Nothing points at Api — the host sits at the top.

Compile-time, not runtime. These arrows are <ProjectReference> edges — what each project needs to build. At runtime a request still flows Controller → Service (Application) → Repository (Infrastructure) → database (see Request Flow). The host references Infrastructure because that is where the module registers its services — binding IProductService to its implementation — and Application is pulled in transitively through it. Learn more — runtime vs references →

The big picture

The host discovers modules at startup and wires them in. Each module is four projects; the "depends on" note on each row is the rule — dependencies point inward to the Domain core, and modules expose only their Contracts.

A module's four layers

Every module (e.g. Catalog) is split into four projects that each have a single responsibility.

Domain

Business Rules & Entities

src/Modules/Catalog/Kheprx.BaseBackend.Catalog.Domain/

Contains the pure business model: aggregate roots, value objects, domain exceptions, and any domain logic that belongs to the core without framework dependencies. This is the innermost layer — it knows nothing about databases, HTTP, or application orchestration.

Depends on: SharedKernel only.

Application

Use-Case Orchestration

src/Modules/Catalog/Kheprx.BaseBackend.Catalog.Application/

Defines and implements the use-case services (e.g. ProductService), alongside the service interfaces, DTOs, FluentValidation validators, and Mapperly mapping profiles. It orchestrates domain objects to fulfil use cases but owns no infrastructure concerns — no EF Core or database dependency. The repository ports it consumes are declared in Domain and implemented by Infrastructure.

Depends on: Domain, SharedKernel.

Infrastructure

Data, DI & External Concerns

src/Modules/Catalog/Kheprx.BaseBackend.Catalog.Infrastructure/

Implements the repository ports declared in Domain. Houses the EF Core DbContext, Npgsql migrations, entity configurations, and the CatalogModule entry point that registers all services with the DI container. It also exposes the module's public API surface by implementing ICatalogModule.

Depends on: Domain, Application, Contracts, SharedKernel.

Contracts

Public Module Interface

src/Modules/Catalog/Kheprx.BaseBackend.Catalog.Contracts/

A thin project containing only the interface(s) that other modules or the host may use to interact with this module — for example ICatalogModule. This is the only project from this module that external code may reference, enforcing a strict boundary.

Depends on: nothing yet — its .csproj is empty (no domain or application types leak out).

Dependency rules

The architecture test suite enforces most of these rules today: Domain​ ​⇛​Infrastructure, Domain​ ​⇛​EF Core, Domain​ ​⇛​Application, Application​ ​⇛​Infrastructure, Application​ ​⇛​EF Core, Infrastructure​ ​⇛​Api, and non-abstract controllers inherit BaseApiController. The remaining rows — Contracts ​→​SharedKernel and cross-module ​→​only .Contracts — are documented conventions that become enforceable as more modules are added.

SharedKernel

Cross-cutting building blocks shared by all modules — never module-specific logic.

SharedKernel

Kheprx.BaseBackend.SharedKernel

src/SharedKernel/Kheprx.BaseBackend.SharedKernel/

Provides BaseEntity (abstract aggregate root with int Id, CreatedAt, and UpdatedAt), DomainException, the IModule interface and ModuleRegistration discovery helper, plus the ApiResponse<T> / BaseApiResponse envelope types. Modules reference SharedKernel but SharedKernel never references any module.
