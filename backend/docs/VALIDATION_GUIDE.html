Kheprx.BaseBackend — Validation Guide

The types of validation, taught from first principles — and a complete catalog of every rule in this codebase.

For the team. This page teaches the kinds of validation and where each belongs, then catalogs every rule we actually enforce. For the layer-by-layer pipeline and the failure-envelope reference, see Validation.

Part 1Learn the concepts

1Four types of validation

Every check answers a different question. Learn the question and you know which type it is — and where it belongs.

Host / Api

1 · Syntactic / structural validation

Asks: "Is the input even well-formed?" — the right type, the right shape, present at all. This runs first and is the cheapest to reject; nothing downstream should assume the input parses.

Owns: presence, type, and shape — is the body parseable, is the required field there, is the route value the right type. Doesn't own: whether the value is acceptable — price: -5 or a 5,000-character name parse perfectly fine and pass straight through to the next layer.

In our code: the {id:int} route constraint (a non-integer id never matches the route → 404) and ASP.NET Core model binding under [ApiController] (a missing or wrong-typed body field → 400 before the action runs).

Kheprx.BaseBackend.Api/Controllers/ProductsController.cs · Kheprx.BaseBackend.Api/Validation/ModelStateResponse.cs
[HttpGet("{id:int}")]   // non-integer id never matches → 404
public sealed record CreateProductRequest(string Name, decimal Price, string? Description);
// Name & Price are non-nullable → treated as required by model binding

Worked example

# non-integer route value
GET /api/products/abc          // id is not an int
→ 404 Not Found              // route never matched — no body

# missing required body field
POST /api/products
{ "price": 9.99 }              // Name omitted
→ 400 Bad Request
{
  "successStatus": false,
  "message": "فشل التحقق من البيانات",
  "error": "The Name field is required.",
  "data": null
}

Elsewhere you would see: "is this a valid email / date / GUID", "is the JSON parseable", "is the required field present".

Pitfall: don't put business rules here — binding only knows "present and the right type", so it will happily accept a negative price or an over-long name. And "required" comes from the type being non-nullable (string Name), not from an attribute; make a field optional by typing it string?.
Application

2 · Semantic / business-rule validation

Asks: "It parses — but does the value make sense?" Ranges, lengths, allowed values, cross-field consistency. These are policy rules: they can change without changing the domain model.

Owns: business rules on the request — required-ness beyond mere presence, length, range, allowed values, cross-field consistency. Doesn't own: well-formedness (binding already guaranteed it) or entity invariants (those must hold even when no HTTP request is involved).

In our code: FluentValidation AbstractValidator<TRequest>, resolved from DI and run by the global ValidationFilter before the action executes.

src/Modules/Identity/Kheprx.BaseBackend.Identity.Application/Validators/AuthRequestValidators.cs
RuleFor(x => x.Email)
    .NotEmpty().WithMessage(_ => CommonMessages.Errors.EmailRequired(AppLanguage.Current))

Every rule attaches a localized message via the lazy .WithMessage(_ => …) form, resolved from a Messages resource class at validation time. Generic field texts (email, password, full name) live in CommonMessages; feature-specific texts (unknown role, invalid status, product name, price) live in the feature's Messages class (UserMessages, AuthMessages, ProductMessages).

Worked example

# well-formed body, but the value is out of range
POST /api/products
{ "name": "Widget", "price": -5 }
→ 400 Bad Request
{
  "successStatus": false,
  "message": "فشل التحقق من البيانات",
  "error": "السعر يجب أن يكون أكبر من صفر",
  "data": null
}

Elsewhere you would see: "price between 0 and 1,000,000", "end date after start date", "status is one of the allowed values".

Pitfall: a validator only runs on the API request path — an internal caller (a background job, another service, a test) bypasses it entirely, which is exactly why the same rule is repeated as a domain invariant below. And rules that need a database lookup ("is this name already taken?") can't be answered from the request alone, so they don't belong here.
Domain

3 · Domain invariant validation

Asks: "Is a rule that must always hold being enforced — no matter how the entity was created or changed?" These rules are intrinsic to the entity, not to one request. Putting the guard inside the entity makes the rule impossible to bypass — whether the object is built from an API call, a background job, a test, or a future use case.

Owns: rules intrinsic to the entity that must hold however it is created or mutated. Doesn't own: friendly per-field request messages (that is the validator's job) or storage concerns.

In our code: guards in Product methods throwing InvalidProductException : DomainException; ExceptionHandlingMiddleware turns any DomainException into a 400 DOMAIN_RULE_VIOLATION.

src/Modules/Catalog/Kheprx.BaseBackend.Catalog.Domain/Entities/Product.cs · …/Exceptions/InvalidProductException.cs
public void ChangePrice(decimal price)
{
    if (price <= 0)
        throw new InvalidProductException("Product price must be greater than zero.");
    Price = price;
}

Worked example

// An internal caller (job, service, test) — no HTTP validator runs:
var product = new Product("", 9.99m);   // blank name
// → Rename("") throws InvalidProductException("Product name is required.")
// Reaching the entity through a request, the middleware returns:
→ 400 Bad Request
{
  "successStatus": false,
  "message": "Product name is required.",
  "error": "DOMAIN_RULE_VIOLATION",
  "data": null
}

Note: this deliberately overlaps with the semantic rule on Price — see defense in depth below. The validator guards the API edge; the domain guards the entity itself.

Pitfall: don't rely on the validator alone for an invariant — anything that builds or changes the entity outside the API would violate it. And always throw a DomainException subtype, not a raw Exception: the middleware maps DomainException to a clean 400, but every other exception becomes a 500.
Infrastructure

4 · Integrity / persistence validation

Asks: "Can the data store itself refuse bad data?" Constraints declared on the database — NOT NULL, length, unique, foreign keys, check constraints. They protect the data even if every check above is bypassed (a direct DB write, a code bug). A safety net, not a UX mechanism — you should rarely hit it.

Owns: last-line storage integrity — NOT NULL, length, unique, foreign keys. It protects the data itself. Doesn't own: user-facing validation — by design it surfaces as a generic 500, not a friendly 400.

In our code: the EF Core fluent configuration, mirrored into the Postgres schema by a migration. A breach throws DbUpdateException → generic 500.

src/Modules/Catalog/Kheprx.BaseBackend.Catalog.Infrastructure/Configurations/ProductConfiguration.cs
builder.Property(p => p.Name).HasMaxLength(200).IsRequired();
builder.Property(p => p.Description).HasMaxLength(2000);
builder.Property(p => p.Price).HasColumnType("numeric(18,2)");
builder.Property(p => p.CreatedAt).IsRequired();

Worked example

// The domain has NO length guard, so a 201-char name slips past it:
product.Rename(new string('x', 201));   // allowed by the entity
await repository.SaveChangesAsync();     // Postgres rejects → DbUpdateException
→ 500 Internal Server Error
{
  "successStatus": false,
  "message": "An unexpected error occurred.",
  "error": "SERVER_ERROR",
  "data": null
}

Elsewhere you would see: a UNIQUE email index, a foreign key to a parent row, CHECK (price > 0).

Pitfall: don't treat it as user-facing validation — it surfaces as a generic 500, not a helpful message. And an EF fluent rule only exists in the database after a migration: adding HasMaxLength(200) without generating and applying a migration changes nothing.
Beyond this template

5 · Two types worth knowing (not yet here)

Uniqueness / referential validation — "does this value already exist, or does the thing it references exist?" It needs a lookup (a repository or database query), so it cannot live in a pure request validator; it belongs in the service/repository, usually backed by a DB unique index or foreign key. The decision table in Validation points such rules at Infrastructure. The Catalog sample has none yet.

Authorization / contextual validation — "is this allowed for this user, in this state?" Frequently confused with validation, but it is a separate concern: a value can be perfectly valid and still forbidden. Keep it out of your validators — it is an authentication / authorization rule, not a shape-or-sense rule.

How the four types map to the five-layer pipeline

The Validation page walks these same checks as a five-layer runtime pipeline — ordered by where each one runs. This guide groups them into four conceptual types — ordered by what kind of check it is. That is why the two numbers do not line up: route constraints and model binding both ask "is it well-formed?", so they fold into one type.

2Four principles

The reasoning that decides where a rule goes — and why the same rule can legitimately appear more than once.

PrincipleWhat it means here
Fail fast, cheapest firstChecks run cheap→expensive: route constraint → model binding → validators → domain → database. The first failure short-circuits, so the costly layers rarely run on bad input.
Defense in depthThe same rule (e.g. price > 0) is enforced at several layers on purpose. Each guards a different entry point: the validator stops a bad HTTP client, the domain stops an internal caller or bug, the database stops a direct write.
Never trust the clientEvery rule on this page is server-side and authoritative. Client-side validation is a UX convenience only — it can always be bypassed, so it is never the source of truth.
Reject vs normalizeReject what is wrong (price ≤ 0 throws); normalize what is merely untidy (a name is trimmed; a blank description becomes null) instead of erroring.

3Application vs Domain invariant — telling them apart

These two enforce overlapping rules yet exist for different reasons, which makes them the easiest pair to confuse. Picture two gates.

Application

The input gate

Checks the request before you build or change the entity — "Is this request acceptable?" It returns a friendly, per-field 400 and then steps aside. It guards the API edge, and only the API edge.

Domain

Business truth

Protects the entity itself, forever — "Can this object exist like this?" The guard lives inside the entity, so the rule holds no matter who builds or mutates it: the API, a background job, a unit test, a data import, or a use case that does not exist yet.

Side by side:

AspectApplication business-ruleDomain invariant
Asks"Is this request valid?""Is this object valid?"
Lives inApplication — AbstractValidator<T>Domain — guards inside the entity

The same rule — price > 0 — can legitimately appear in both: the validator returns a friendly 400 before any work runs, and the domain makes an invalid Product impossible to construct. That is not duplication; it is defense in depth.

The decision rule — ask yourself:

Ask yourself……and if the answer is yes
"Should this rule always be true for the entity, no matter where it is used?"Domain invariant — e.g. price > 0 · an order cannot complete with no items · an invoice cannot be paid twice
"Is it mainly about accepting or rejecting this request?"Application — e.g. description ≤ 2000 · page size 1–100 · DateFrom before DateTo · SortBy in an allowed set
Pitfall: keep Domain guards framework-free. Throw a DomainException — never BadRequestException, ApiResponse.Failure(…), or ModelState.AddModelError(…). The Domain must not know about HTTP, controllers, ApiResponse, FluentValidation, or EF Core — that is what keeps it the innermost, dependency-free layer.
Mental model. Application validation gives friendly request-level errors; the Domain invariant guarantees the business object can never enter an invalid state — even when no validator runs.

6Add a validation rule

  1. Name the type first Decide which question the rule answers — well-formed (syntactic), makes-sense (business), always-true (invariant), or storage-safe (integrity). That picks the layer.
  2. Business rule → FluentValidation Add or extend the AbstractValidator<TRequest> in .Application/Validators/. The global ValidationFilter picks it up automatically.
  3. Always-true invariant → Domain guard Add a guard in the entity constructor or method that throws a DomainException subtype, so no caller can bypass it.
  4. Storage integrity → EF constraint Add the constraint in the entity's IEntityTypeConfiguration<T> and generate a migration.
  5. Run dotnet test Confirm the solution stays green and warning-clean.
