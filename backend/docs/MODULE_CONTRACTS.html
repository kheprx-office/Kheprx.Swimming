ICatalogModule — the public interface

src/Modules/Catalog/Kheprx.BaseBackend.Catalog.Contracts/ICatalogModule.cs

The single interface that defines what the Catalog module exposes to the rest of the system — nothing more.

namespace Kheprx.BaseBackend.Catalog.Contracts;

public interface ICatalogModule
{
    Task<bool> ProductExistsAsync(int productId, CancellationToken ct = default);
}

What's happening here: ICatalogModule is the Catalog module's only outward-facing contract. Any other module (or the host) that needs to ask "does this product exist?" depends on this interface, never on Infrastructure directly. The single method ProductExistsAsync is intentionally narrow — it exposes exactly what cross-module callers need and nothing else. The concrete implementation, CatalogModuleApi, lives in Infrastructure and is registered with the DI container at startup.

Kheprx.BaseBackend.Catalog.Contracts.csproj — the empty project file

src/Modules/Catalog/Kheprx.BaseBackend.Catalog.Contracts/Kheprx.BaseBackend.Catalog.Contracts.csproj

The .csproj contains no <ItemGroup> or <PackageReference> entries — it references nothing, not even SharedKernel. This is deliberate: the boundary is kept as thin as possible so any module can take a reference to Contracts without pulling in a transitive dependency chain. It is the only Catalog project that other modules are permitted to reference; see the reference graph for how the dependency arrows flow.

In simple words: Contracts is a tiny, dependency-free island. It declares what the Catalog module can do for others (ICatalogModule), but says nothing about how. The implementation lives in Infrastructure — CatalogModuleApi — which is wired up at runtime without any module needing to know about it.
