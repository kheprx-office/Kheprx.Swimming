Convention The IModule convention

How every module self-registers: one interface, one discovery scan, one call in Program.cs.

← Back to Module Anatomy

Lives in SharedKernel · implemented by each module's Infrastructure · invoked by the Host / Api.

The IModule convention is the glue between independent modules and the host. Each module's Infrastructure project implements IModule and registers its own services — no manual wiring in Program.cs needed. At startup, AddModules in SharedKernel probes every Kheprx.BaseBackend.*.dll in the output directory, reflects out every concrete IModule implementation it finds, and calls Register on each. The four files below tell the whole story.

Files in this convention

SharedKernel

IModule — the contract

src/SharedKernel/Kheprx.BaseBackend.SharedKernel/Modules/IModule.cs

A single-method interface that every module's Infrastructure layer must implement. By depending on this interface rather than concrete registrations, the host stays completely ignorant of any specific module.

using Microsoft.Extensions.Configuration;
using Microsoft.Extensions.DependencyInjection;

namespace Kheprx.BaseBackend.SharedKernel.Modules;

public interface IModule
{
    IServiceCollection Register(IServiceCollection services, IConfiguration configuration);
}

What's happening here: Register receives the DI container and the app configuration, and is expected to add everything the module needs — DbContext, repositories, services, mappers. The caller (AddModules) does not need to know which modules exist; it just calls Register on whatever it discovers.

SharedKernel

ModuleRegistration — the discovery scan

src/SharedKernel/Kheprx.BaseBackend.SharedKernel/Modules/ModuleRegistration.cs

The AddModules extension method. It scans every Kheprx.BaseBackend.*.dll in the output folder, loads any not yet loaded, reflects out every concrete IModule implementation, and calls Register on each one.

using System.Reflection;
using Microsoft.Extensions.Configuration;
using Microsoft.Extensions.DependencyInjection;

namespace Kheprx.BaseBackend.SharedKernel.Modules;

public static class ModuleRegistration
{
    public static IServiceCollection AddModules(this IServiceCollection services, IConfiguration configuration)
    {
        foreach (var module in DiscoverModules())
            module.Register(services, configuration);
        return services;
    }

    private static IEnumerable<IModule> DiscoverModules()
    {
        var loaded = new HashSet<string>(
            AppDomain.CurrentDomain.GetAssemblies().Select(a => a.GetName().Name!));

        foreach (var dll in Directory.GetFiles(AppContext.BaseDirectory, "Kheprx.BaseBackend.*.dll"))
        {
            var name = Path.GetFileNameWithoutExtension(dll);
            if (loaded.Add(name))
            {
                try { Assembly.LoadFrom(dll); }
                catch { /* skip assemblies that cannot be loaded */ }
            }
        }

        var moduleType = typeof(IModule);
        return AppDomain.CurrentDomain.GetAssemblies()
            .SelectMany(SafeGetTypes)
            .Where(t => moduleType.IsAssignableFrom(t) && t is { IsClass: true, IsAbstract: false })
            .Select(t => (IModule)Activator.CreateInstance(t)!);
    }

    private static IEnumerable<Type> SafeGetTypes(Assembly assembly)
    {
        try { return assembly.GetTypes(); }
        catch (ReflectionTypeLoadException ex) { return ex.Types.Where(t => t is not null)!; }
    }
}

What's happening here: DiscoverModules first builds a set of already-loaded assembly names, then walks Kheprx.BaseBackend.*.dll files on disk and calls Assembly.LoadFrom for any not yet in memory. After that it queries all loaded assemblies for non-abstract classes that implement IModule, instantiates each via Activator.CreateInstance, and returns them. SafeGetTypes guards against partially-loaded assemblies by catching ReflectionTypeLoadException. Adding a new module to the solution is enough — no registration change is needed in the host.

Infrastructure

CatalogModule — a real implementation

src/Modules/Catalog/Kheprx.BaseBackend.Catalog.Infrastructure/CatalogModule.cs

The Catalog module's concrete IModule. It registers the DbContext, the Mapperly mapper, the repository, the application service, and the public module API — all scoped or singleton as appropriate.

using Kheprx.BaseBackend.Catalog.Application.Mappings;
using Kheprx.BaseBackend.Catalog.Application.Services;
using Kheprx.BaseBackend.Catalog.Application.Services.Interfaces;
using Kheprx.BaseBackend.Catalog.Contracts;
using Kheprx.BaseBackend.Catalog.Domain.Repositories;
using Kheprx.BaseBackend.Catalog.Infrastructure.Data;
using Kheprx.BaseBackend.Catalog.Infrastructure.Repositories;
using Kheprx.BaseBackend.Catalog.Infrastructure.Services;
using Kheprx.BaseBackend.SharedKernel.Modules;
using Microsoft.EntityFrameworkCore;
using Microsoft.Extensions.Configuration;
using Microsoft.Extensions.DependencyInjection;

namespace Kheprx.BaseBackend.Catalog.Infrastructure;

public sealed class CatalogModule : IModule
{
    public IServiceCollection Register(IServiceCollection services, IConfiguration configuration)
    {
        services.AddDbContext<CatalogDbContext>(options =>
            options.UseNpgsql(configuration.GetConnectionString("Postgres")));

        services.AddSingleton<CatalogMapper>();
        services.AddScoped<IProductRepository, ProductRepository>();
        services.AddScoped<IProductService, ProductService>();
        services.AddScoped<ICatalogModule, CatalogModuleApi>();
        return services;
    }
}

What's happening here: this is the only place in the entire Catalog module where service registrations are declared. CatalogDbContext gets the Postgres connection string from configuration; CatalogMapper (Mapperly-generated) is a singleton because it is stateless; repository, service, and the public ICatalogModule facade are all scoped to the HTTP request. When AddModules discovers and instantiates this class, it calls Register — and the Catalog module is fully wired.

Host / Api

Program.cs — the single call site

Kheprx.BaseBackend.Api/Program.cs

The application entry point. One line — builder.Services.AddModules(builder.Configuration) — triggers the discovery scan and registers every module in the solution.

using Kheprx.BaseBackend.Api.Extensions;
using Kheprx.BaseBackend.SharedKernel.Modules;
using Serilog;

var builder = WebApplication.CreateBuilder(args);

builder.Host.UseSerilog((context, loggerConfiguration) =>
    loggerConfiguration.ReadFrom.Configuration(context.Configuration));

builder.Services.AddModules(builder.Configuration);
builder.Services.AddSharedInfrastructure(builder.Configuration);

var app = builder.Build();
app.UseSharedPipeline(app.Environment);
app.Run();

What's happening here: AddModules is called before AddSharedInfrastructure, so every module's services are registered first and shared infrastructure (middleware, exception handling, etc.) is layered on top. The host imports only Kheprx.BaseBackend.SharedKernel.Modules — it has no compile-time reference to any module assembly. Module assemblies are discovered purely at runtime from the output directory.

In simple words: IModule is a one-method contract declared in SharedKernel. Each module's Infrastructure project implements it and registers its own services inside Register. At startup, AddModules walks every Kheprx.BaseBackend.*.dll in the output folder, reflects out every concrete IModule, and calls Register on each. Adding a new module to the solution requires no change in Program.cs — just implement IModule in the new module's Infrastructure project and drop the assembly next to the host.
