IProductService — the use-case contract

src/Modules/Catalog/Kheprx.BaseBackend.Catalog.Application/Services/Interfaces/IProductService.cs

The service interface that Controllers depend on. It speaks in DTOs, not in domain entities, so the HTTP layer never touches Product directly.

using Kheprx.BaseBackend.Catalog.Application.DTOs;

namespace Kheprx.BaseBackend.Catalog.Application.Services.Interfaces;

public interface IProductService
{
    Task<IReadOnlyList<ProductDto>> GetAllAsync(CancellationToken ct = default);
    Task<ProductDto?> GetByIdAsync(int id, CancellationToken ct = default);
    Task<ProductDto> CreateAsync(CreateProductRequest request, CancellationToken ct = default);
    Task<ProductDto?> UpdateAsync(int id, UpdateProductRequest request, CancellationToken ct = default);
    Task<bool> DeleteAsync(int id, CancellationToken ct = default);
}

What's happening here: IProductService defines the five use-cases the Catalog module exposes (list, get, create, update, delete). The controller (in the Host / Api) injects this interface; at runtime the DI container resolves it to ProductService. Returning null on get/update/delete signals "not found" without throwing — the controller translates that to a 404. The interface deals only in Application-layer DTOs (like ProductDto), never Domain entities directly.

ProductService — the use-case implementation

src/Modules/Catalog/Kheprx.BaseBackend.Catalog.Application/Services/ProductService.cs

The internal sealed implementation of IProductService. It coordinates the repository and mapper but contains no business rules — those live in the Domain entities.

using Kheprx.BaseBackend.Catalog.Application.DTOs;
using Kheprx.BaseBackend.Catalog.Application.Mappings;
using Kheprx.BaseBackend.Catalog.Application.Services.Interfaces;
using Kheprx.BaseBackend.Catalog.Domain.Entities;
using Kheprx.BaseBackend.Catalog.Domain.Repositories;

namespace Kheprx.BaseBackend.Catalog.Application.Services;

internal sealed class ProductService : IProductService
{
    private readonly IProductRepository _repository;
    private readonly CatalogMapper _mapper;

    public ProductService(IProductRepository repository, CatalogMapper mapper)
    {
        _repository = repository;
        _mapper = mapper;
    }

    public async Task<IReadOnlyList<ProductDto>> GetAllAsync(CancellationToken ct = default)
        => _mapper.ToDtoList(await _repository.GetAllAsync(ct));

    public async Task<ProductDto?> GetByIdAsync(int id, CancellationToken ct = default)
    {
        var product = await _repository.GetByIdAsync(id, ct);
        return product is null ? null : _mapper.ToDto(product);
    }

    public async Task<ProductDto> CreateAsync(CreateProductRequest request, CancellationToken ct = default)
    {
        var product = new Product(request.Name, request.Price, request.Description);
        await _repository.AddAsync(product, ct);
        await _repository.SaveChangesAsync(ct);
        return _mapper.ToDto(product);
    }

    public async Task<ProductDto?> UpdateAsync(int id, UpdateProductRequest request, CancellationToken ct = default)
    {
        var product = await _repository.GetByIdAsync(id, ct);
        if (product is null) return null;

        product.Rename(request.Name);
        product.ChangePrice(request.Price);
        product.UpdateDescription(request.Description);
        await _repository.SaveChangesAsync(ct);
        return _mapper.ToDto(product);
    }

    public async Task<bool> DeleteAsync(int id, CancellationToken ct = default)
    {
        var product = await _repository.GetByIdAsync(id, ct);
        if (product is null) return false;

        _repository.Remove(product);
        await _repository.SaveChangesAsync(ct);
        return true;
    }
}

What's happening here: the class is internal sealed — it cannot be referenced from outside the assembly; the DI registration in the module's extension method is the only place that wires it up. Every method follows the same pattern: call the repository (via the Domain interface IProductRepository), call domain methods on the entity if needed, persist, and map the result to a DTO. SaveChangesAsync is called explicitly after mutations, giving the service full control over the transaction boundary. See Request Flow for how this fits into the full pipeline.

ProductDtos — the data shapes

src/Modules/Catalog/Kheprx.BaseBackend.Catalog.Application/DTOs/ProductDtos.cs

Three immutable record types: the outbound read shape (ProductDto) and the two inbound write shapes (CreateProductRequest, UpdateProductRequest).

namespace Kheprx.BaseBackend.Catalog.Application.DTOs;

public sealed record ProductDto(
    int Id, string Name, string? Description, decimal Price, DateTime CreatedAt, DateTime? UpdatedAt);

public sealed record CreateProductRequest(string Name, decimal Price, string? Description);

public sealed record UpdateProductRequest(string Name, decimal Price, string? Description);

What's happening here: positional record types give value-based equality and a compact syntax for pure data carriers. ProductDto exposes every field a client might need, including CreatedAt/UpdatedAt from BaseEntity. The request records intentionally omit Id — the id always comes from the route, not the body, preventing mass-assignment bugs. Description is nullable in all three shapes because it is optional in the domain.

ProductRequestValidators — FluentValidation rules

src/Modules/Catalog/Kheprx.BaseBackend.Catalog.Application/Validators/ProductRequestValidators.cs

Two FluentValidation validators — one for create, one for update — that enforce the same shape rules on inbound requests before they reach the service.

using Kheprx.BaseBackend.Catalog.Application.DTOs;
using FluentValidation;

namespace Kheprx.BaseBackend.Catalog.Application.Validators;

public sealed class CreateProductRequestValidator : AbstractValidator<CreateProductRequest>
{
    public CreateProductRequestValidator()
    {
        RuleFor(x => x.Name).NotEmpty().MaximumLength(200);
        RuleFor(x => x.Price).GreaterThan(0);
        RuleFor(x => x.Description).MaximumLength(2000);
    }
}

public sealed class UpdateProductRequestValidator : AbstractValidator<UpdateProductRequest>
{
    public UpdateProductRequestValidator()
    {
        RuleFor(x => x.Name).NotEmpty().MaximumLength(200);
        RuleFor(x => x.Price).GreaterThan(0);
        RuleFor(x => x.Description).MaximumLength(2000);
    }
}

What's happening here: both validators mirror each other because create and update share the same required fields. Validators are registered automatically by the module's DI extension via AddValidatorsFromAssemblyContaining; the host's validation pipeline calls them before the controller action body runs, so the service and domain never receive malformed input. Note that the domain also enforces these invariants itself (e.g. Price > 0) — FluentValidation is the fast, user-friendly first gate; the domain guard is the authoritative last gate.

ProductMessages — localized response messages

src/Modules/Catalog/Kheprx.BaseBackend.Catalog.Application/Resources/ProductMessages.cs

Resources/ — static …Messages classes (nested Errors/Success, one method per message, lang-switch: "ar" → Arabic, default → English). Identity: AuthMessages, UserMessages, RoleMessages. Catalog: ProductMessages.

What's happening here: the lang-switch pattern keeps strings close to the code that uses them. Controllers call methods like ProductMessages.Errors.ProductNotFound(AppLanguage.Current) instead of inline string literals. Identity modules have equivalent classes (AuthMessages, UserMessages, RoleMessages); shared field texts (email, password, full name) live in CommonMessages in SharedKernel. See SharedKernel for the AppLanguage and CommonMessages classes.

CatalogMapper — Mapperly source-generated mapper

src/Modules/Catalog/Kheprx.BaseBackend.Catalog.Application/Mappings/CatalogMapper.cs

A partial class annotated with [Mapper]; the Mapperly source generator fills in the method bodies at compile time — no reflection, no runtime overhead.

using Kheprx.BaseBackend.Catalog.Application.DTOs;
using Kheprx.BaseBackend.Catalog.Domain.Entities;
using Riok.Mapperly.Abstractions;

namespace Kheprx.BaseBackend.Catalog.Application.Mappings;

[Mapper]
public partial class CatalogMapper
{
    public partial ProductDto ToDto(Product product);
    public partial IReadOnlyList<ProductDto> ToDtoList(IReadOnlyList<Product> products);
}

What's happening here: declaring a method as partial with no body is the Mapperly convention — the source generator inspects the source and target types, matches properties by name and type, and emits a concrete implementation in a generated file. Because the mapping is generated at build time, there are no advisory suppressions and no hidden object casts: if a property is missing or incompatible, the build fails rather than silently producing wrong data. ToDtoList maps an entire collection in one call, keeping ProductService clean.

In simple words: The Application layer is the conductor. It owns IProductService (what can be done), ProductService (how to do it — coordinate the Domain and repository), DTOs (the data shapes that cross layer boundaries), validators (fast input checks before anything reaches the domain), the mapper (zero-cost conversion from entity to DTO), and message resource classes (localized response text that controllers and validators read from …Messages static classes rather than inline string literals). When a request arrives it flows through the validator, into the service, which calls Domain methods, persists via IProductRepository, and hands back a DTO — all of this wiring is visible in the Request Flow diagram.
