Kheprx.BaseBackend — Validation

Five layers of validation, from the HTTP edge to the database. Each owns a different kind of rule.

Fail fast, cheapest first. A request is checked at five points on its way in. Body validation (layers 2–4) all return the same ApiResponse<T> envelope. New to the topic? The Validation Guide teaches the types and catalogs every rule.
Runs in: Host / ApiApplication DomainInfrastructure

The validation pipeline

A request passes these checks in order. The first one that fails short-circuits with a response.

1 · Route constraintsHost / Api① Syntactic / structural
[HttpGet("{id:int}")] — malformed id never matches → 404
↓route matched
2 · Model binding / [ApiController]Host / Api① Syntactic / structural
missing or malformed fields → 400 ApiResponse "Validation failed"
↓body bound
3 · FluentValidation (ValidationFilter)Application② Semantic / business-rule
request-DTO business rules → 400 ApiResponse "Validation failed"
↓request valid
4 · Domain invariantsDomain③ Domain invariant
entity guards throw DomainException → 400 ApiResponse "DOMAIN_RULE_VIOLATION"
↓invariants hold
5 · Persistence constraintsInfrastructure④ Integrity / persistence
EF/DB integrity backstop → 500 on breach
Layers vs. types. These five entries are runtime layers — ordered by where each check runs. The Validation Guide groups them into four conceptual types (by what kind of check it is), so the numbers do not match: layers 1 and 2 are both the "syntactic" type. The guide has the full mapping table.

The five layers

Host / Api

Layer 1 — Route constraints

Kheprx.BaseBackend.Api/Controllers/ProductsController.cs
[HttpGet("{id:int}")]
public async Task<ActionResult<ApiResponse<ProductDto>>> GetById(int id, CancellationToken ct)

The :int route constraint rejects a non-integer id at routing time — the route simply does not match, so the client gets a 404 and the action never runs.

Owns: route value shape / type.

Failure response: 404 — no body.

Host / Api

Layer 2 — Model binding / [ApiController]

Kheprx.BaseBackend.Api/Validation/ModelStateResponse.cs · Kheprx.BaseBackend.Api/Extensions/ServiceCollectionExtensions.cs
// ServiceCollectionExtensions.cs
.ConfigureApiBehaviorOptions(options =>
    options.InvalidModelStateResponseFactory = context =>
        new BadRequestObjectResult(ModelStateResponse.From(context.ModelState)));

// ModelStateResponse.From(...)
public static ApiResponse<object> From(ModelStateDictionary modelState)
{
    var errors = string.Join("; ", modelState.Values
        .SelectMany(entry => entry.Errors)
        .Select(error => error.ErrorMessage)
        .Where(message => !string.IsNullOrWhiteSpace(message)));

    if (string.IsNullOrWhiteSpace(errors))
        errors = CommonMessages.Errors.ValidationFallback(AppLanguage.Current);

    return ApiResponse<object>.Failure(CommonMessages.Errors.ValidationFailed(AppLanguage.Current), errors);
}

[ApiController] (on BaseApiController) runs automatic model-state validation. Non-nullable request properties are treated as required, so a missing or wrong-typed field fails binding. The InvalidModelStateResponseFactory converts that failure into the same ApiResponse.Failure(CommonMessages.Errors.ValidationFailed(AppLanguage.Current), …) envelope the rest of the stack uses. CommonMessages lives in SharedKernel/Resources and returns Arabic for the current app language, with English as the default arm.

Owns: presence / shape / type of the request body.

Failure response: 400 ApiResponse.Failure(CommonMessages.Errors.ValidationFailed(AppLanguage.Current), joinedErrors).

Application

Layer 3 — FluentValidation

src/Modules/Catalog/Kheprx.BaseBackend.Catalog.Application/Validators/ProductRequestValidators.cs (run by Kheprx.BaseBackend.Api/Filters/ValidationFilter.cs)
public sealed class CreateProductRequestValidator : AbstractValidator<CreateProductRequest>
{
    public CreateProductRequestValidator()
    {
        RuleFor(x => x.Name).NotEmpty().MaximumLength(200);
        RuleFor(x => x.Price).GreaterThan(0);
        RuleFor(x => x.Description).MaximumLength(2000);
    }
}

The global ValidationFilter resolves the matching IValidator<T> for each action argument from DI and runs it before the action; on failure it returns 400 ApiResponse.Failure(CommonMessages.Errors.ValidationFailed(AppLanguage.Current), joinedErrors). Validators are auto-registered by AddValidatorsFromAssemblies.

Owns: business rules on the request DTO (required, length, range).

Failure response: 400 ApiResponse.Failure(CommonMessages.Errors.ValidationFailed(AppLanguage.Current), joinedErrors).

Domain

Layer 4 — Domain invariants

src/Modules/Catalog/Kheprx.BaseBackend.Catalog.Domain/Entities/Product.cs → Kheprx.BaseBackend.Api/Middlewares/ExceptionHandlingMiddleware.cs
public void ChangePrice(decimal price)
{
    if (price <= 0)
        throw new InvalidProductException("Product price must be greater than zero.");
    Price = price;
    Touch();
}

Invariants that must hold no matter how the entity is created or mutated live as guards inside entity methods, throwing an InvalidProductException : DomainException. ExceptionHandlingMiddleware catches any DomainException and returns 400 ApiResponse.Failure(message, "DOMAIN_RULE_VIOLATION"). This is the last line of defense — it holds even if a caller bypasses the DTO validators.

Owns: entity invariants.

Failure response: 400 ApiResponse.Failure(message, "DOMAIN_RULE_VIOLATION").

Infrastructure

Layer 5 — Persistence constraints

src/Modules/Catalog/Kheprx.BaseBackend.Catalog.Infrastructure/Configurations/ProductConfiguration.cs
builder.Property(p => p.Name).HasMaxLength(200).IsRequired();
builder.Property(p => p.Description).HasMaxLength(2000);
builder.Property(p => p.Price).HasColumnType("numeric(18,2)");

The EF Core fluent configuration mirrors the DTO rules as database constraints — defense in depth. A violation that somehow reaches the database throws DbUpdateException, which ExceptionHandlingMiddleware turns into a generic 500. You should rarely hit this layer; it exists so the data can never be corrupted.

Owns: storage integrity.

Failure response: 500 (generic server error — this layer should never be reached in normal operation).

One envelope for every failure

Layers 2–4 all return the same ApiResponse<T> shape — only the error field differs.

  "successStatus": false,
  "message": "Validation failed",
  "error": "'Price' must be greater than '0'.",
  "data": null
}

Add a validation rule

  1. Decide the layer Use the decision table above to pick where the rule belongs.
  2. Request-shape rule → FluentValidation Add or extend the AbstractValidator<TRequest> in the module's .Application/Validators/. The global ValidationFilter picks it up automatically — no wiring needed.
  3. Entity invariant → Domain guard Add a guard in the entity constructor or method that throws a DomainException subtype. ExceptionHandlingMiddleware converts it to a 400 envelope.
  4. Storage integrity → EF constraint Add the constraint in the entity's IEntityTypeConfiguration<T> and generate a migration.
  5. Run dotnet test Confirm the solution stays green and warning-clean.
