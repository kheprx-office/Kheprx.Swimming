CatalogModule — DI registration entry point

src/Modules/Catalog/Kheprx.BaseBackend.Catalog.Infrastructure/CatalogModule.cs

Implements IModule and wires every Catalog service, repository, and DbContext into the DI container in one place.

using Kheprx.BaseBackend.Catalog.Application.Mappings;
using Kheprx.BaseBackend.Catalog.Application.Services;
using Kheprx.BaseBackend.Catalog.Application.Services.Interfaces;
using Kheprx.BaseBackend.Catalog.Contracts;
using Kheprx.BaseBackend.Catalog.Domain.Repositories;
using Kheprx.BaseBackend.Catalog.Infrastructure.Data;
using Kheprx.BaseBackend.Catalog.Infrastructure.Repositories;
using Kheprx.BaseBackend.Catalog.Infrastructure.Services;
using Kheprx.BaseBackend.SharedKernel.Modules;
using Microsoft.EntityFrameworkCore;
using Microsoft.Extensions.Configuration;
using Microsoft.Extensions.DependencyInjection;

namespace Kheprx.BaseBackend.Catalog.Infrastructure;

public sealed class CatalogModule : IModule
{
    public IServiceCollection Register(IServiceCollection services, IConfiguration configuration)
    {
        services.AddDbContext<CatalogDbContext>(options =>
            options.UseNpgsql(configuration.GetConnectionString("Postgres")));

        services.AddSingleton<CatalogMapper>();
        services.AddScoped<IProductRepository, ProductRepository>();
        services.AddScoped<IProductService, ProductService>();
        services.AddScoped<ICatalogModule, CatalogModuleApi>();
        return services;
    }
}

What's happening here: CatalogModule implements the IModule interface (from SharedKernel). The Host calls Register at startup, handing each module a chance to configure its own slice of the DI container. Here it registers CatalogDbContext with a Npgsql connection string, the singleton CatalogMapper, and three scoped bindings: the IProductRepository port mapped to ProductRepository, the IProductService Application interface mapped to ProductService, and the ICatalogModule Contracts interface mapped to CatalogModuleApi. See The IModule convention for how the Host discovers and calls all modules.

CatalogDbContext — the EF Core unit of work

src/Modules/Catalog/Kheprx.BaseBackend.Catalog.Infrastructure/Data/CatalogDbContext.cs

The module's DbContext, exposing the Products set and wiring all IEntityTypeConfiguration implementations automatically.

using Kheprx.BaseBackend.Catalog.Domain.Entities;
using Microsoft.EntityFrameworkCore;

namespace Kheprx.BaseBackend.Catalog.Infrastructure.Data;

public sealed class CatalogDbContext : DbContext
{
    public CatalogDbContext(DbContextOptions<CatalogDbContext> options) : base(options) { }

    public DbSet<Product> Products => Set<Product>();

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.ApplyConfigurationsFromAssembly(typeof(CatalogDbContext).Assembly);
        base.OnModelCreating(modelBuilder);
    }
}

What's happening here: CatalogDbContext inherits from EF Core's DbContext. The Products property is a computed expression that calls Set<Product>(), making EF Core the single source of truth for the underlying set. OnModelCreating calls ApplyConfigurationsFromAssembly, which scans this assembly and applies every class that implements IEntityTypeConfiguration<T> — so ProductConfiguration is picked up automatically without being listed explicitly.

CatalogDbContextFactory — design-time factory

src/Modules/Catalog/Kheprx.BaseBackend.Catalog.Infrastructure/Data/CatalogDbContextFactory.cs

Implements IDesignTimeDbContextFactory so the dotnet ef CLI can create a CatalogDbContext without the Host application running.

using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Design;

namespace Kheprx.BaseBackend.Catalog.Infrastructure.Data;

// Design-time factory used by `dotnet ef` (migrations/scaffolding). Uses a local-dev connection string;
// at runtime the application uses ConnectionStrings:Postgres from configuration instead.
public sealed class CatalogDbContextFactory : IDesignTimeDbContextFactory<CatalogDbContext>
{
    public CatalogDbContext CreateDbContext(string[] args)
    {
        var options = new DbContextOptionsBuilder<CatalogDbContext>()
            .UseNpgsql("Host=localhost;Port=5432;Database=basebackend;Username=postgres;Password=postgres")
            .Options;
        return new CatalogDbContext(options);
    }
}

What's happening here: when you run dotnet ef migrations add or dotnet ef database update, the EF Core tooling looks for an IDesignTimeDbContextFactory<T> in the assembly. CatalogDbContextFactory satisfies that requirement by building a DbContextOptions with a hardcoded local-dev Npgsql connection string. At runtime, CatalogModule.Register replaces this with the connection string from app configuration — the factory is never called by the running application.

ProductConfiguration — entity-to-table mapping

src/Modules/Catalog/Kheprx.BaseBackend.Catalog.Infrastructure/Configurations/ProductConfiguration.cs

Tells EF Core exactly how to map the Product entity to the products table — column types, lengths, and nullability constraints.

using Kheprx.BaseBackend.Catalog.Domain.Entities;
using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Metadata.Builders;

namespace Kheprx.BaseBackend.Catalog.Infrastructure.Configurations;

internal sealed class ProductConfiguration : IEntityTypeConfiguration<Product>
{
    public void Configure(EntityTypeBuilder<Product> builder)
    {
        builder.ToTable("products");
        builder.HasKey(p => p.Id);
        builder.Property(p => p.Name).HasMaxLength(200).IsRequired();
        builder.Property(p => p.Description).HasMaxLength(2000);
        builder.Property(p => p.Price).HasColumnType("numeric(18,2)");
        builder.Property(p => p.CreatedAt).IsRequired();
    }
}

What's happening here: this class implements IEntityTypeConfiguration<Product>, which CatalogDbContext.OnModelCreating discovers automatically via assembly scanning. It maps the entity to a snake-case table name products, sets the primary key on Id, constrains Name to 200 characters (required), Description to 2000 characters (nullable), and fixes the Price column to numeric(18,2) for exact decimal storage. CreatedAt is marked required so the database column is non-nullable. Domain properties with private setters are mapped transparently by EF Core — no Domain code needs to change.

ProductRepository — port implementation

src/Modules/Catalog/Kheprx.BaseBackend.Catalog.Infrastructure/Repositories/ProductRepository.cs

The concrete EF Core implementation of the IProductRepository port declared in Domain.

using Kheprx.BaseBackend.Catalog.Domain.Entities;
using Kheprx.BaseBackend.Catalog.Domain.Repositories;
using Kheprx.BaseBackend.Catalog.Infrastructure.Data;
using Microsoft.EntityFrameworkCore;

namespace Kheprx.BaseBackend.Catalog.Infrastructure.Repositories;

internal sealed class ProductRepository : IProductRepository
{
    private readonly CatalogDbContext _db;

    public ProductRepository(CatalogDbContext db) => _db = db;

    public async Task<IReadOnlyList<Product>> GetAllAsync(CancellationToken ct = default)
        => await _db.Products.AsNoTracking().OrderBy(p => p.Id).ToListAsync(ct);

    public Task<Product?> GetByIdAsync(int id, CancellationToken ct = default)
        => _db.Products.FirstOrDefaultAsync(p => p.Id == id, ct);

    public async Task AddAsync(Product product, CancellationToken ct = default)
        => await _db.Products.AddAsync(product, ct);

    public void Remove(Product product) => _db.Products.Remove(product);

    public Task<bool> ExistsAsync(int id, CancellationToken ct = default)
        => _db.Products.AnyAsync(p => p.Id == id, ct);

    public Task SaveChangesAsync(CancellationToken ct = default) => _db.SaveChangesAsync(ct);
}

What's happening here: ProductRepository is internal sealed — only the DI container (wired in CatalogModule) ever touches it; all other layers depend on the Domain interface IProductRepository. GetAllAsync uses AsNoTracking() for read-only list queries to avoid change-tracking overhead. GetByIdAsync returns a tracked entity, while ExistsAsync uses AnyAsync to probe existence without materializing a row. SaveChangesAsync delegates to EF Core's DbContext.SaveChangesAsync, making the Application layer responsible for deciding when to commit a unit of work.

CatalogModuleApi — cross-module facade

src/Modules/Catalog/Kheprx.BaseBackend.Catalog.Infrastructure/Services/CatalogModuleApi.cs

Implements the ICatalogModule Contracts interface, exposing a narrow public API that other modules can call without depending on Catalog internals.

using Kheprx.BaseBackend.Catalog.Contracts;
using Kheprx.BaseBackend.Catalog.Domain.Repositories;

namespace Kheprx.BaseBackend.Catalog.Infrastructure.Services;

internal sealed class CatalogModuleApi : ICatalogModule
{
    private readonly IProductRepository _repository;

    public CatalogModuleApi(IProductRepository repository) => _repository = repository;

    public Task<bool> ProductExistsAsync(int productId, CancellationToken ct = default)
        => _repository.ExistsAsync(productId, ct);
}

What's happening here: ICatalogModule is declared in the Contracts project and lists only what other modules need from Catalog — here, a single ProductExistsAsync check. CatalogModuleApi fulfils that contract by delegating straight to IProductRepository.ExistsAsync. This keeps the cross-module boundary thin: external callers never see ProductRepository, CatalogDbContext, or any Application service — only the Contracts interface. The class is internal even though it satisfies a public interface; the DI container resolves it by the interface type.

Migrations/ — EF Core generated migrations

src/Modules/Catalog/Kheprx.BaseBackend.Catalog.Infrastructure/Migrations/

This folder holds the EF Core migration files produced by dotnet ef migrations add.

What's happening here: the folder contains at least one migration (e.g. …_InitialCatalog) and the CatalogDbContextModelSnapshot class that EF Core uses to track the current model state. Migration files are generated — not hand-written — and should not be edited directly. At startup (or deploy), migrations are applied to the database so the schema stays in sync with the entity and configuration classes above. Because the content is machine-generated and can be regenerated from the model at any time, the raw code is not reproduced here.

In simple words: Infrastructure is the only layer that touches the database. It registers everything the module needs into DI (CatalogModule), tells EF Core how to map the Product entity (ProductConfiguration), stores and retrieves data (ProductRepository), and exposes a thin facade to other modules (CatalogModuleApi). Domain declares the ports; Infrastructure implements them — see Domain for the interfaces. See The IModule convention for how CatalogModule.Register is discovered and called.
