Kheprx.BaseBackend — Two Flows: Runtime vs Project References

Why the runtime call path and the compile-time project references point in different directions — from first principles, with the real code.

Your thinking is correct. A request really does flow API → Application → Infrastructure → database. The architecture diagram that shows API → Infrastructure is drawing something else — project references (startup wiring), not the request path. This page untangles the two.

1 · The runtime request flow

What actually happens, top to bottom, when someone calls GET /api/products.

HTTP request
GET /api/products
↓ routed to the controller
Host / Api ProductsController
Kheprx.BaseBackend.Api/Controllers/ProductsController.cs
↓ calls IProductService
Application ProductService
Application/Services/ProductService.cs
↓ calls IProductRepository (a Domain port)
Infrastructure ProductRepository
Infrastructure/Repositories/ProductRepository.cs
↓ uses
Infrastructure CatalogDbContext
Infrastructure/Data/CatalogDbContext.cs
↓ SQL
External PostgreSQL

So yes — the real request path is API → Application → Infrastructure → database. But there is one subtlety that makes the whole architecture work:

Application never names Infrastructure. It only knows an interface. The Application service asks for IProductRepository — and that interface is declared in Domain, not Infrastructure.

The Application service depends on the interface:

internal sealed class ProductService : IProductService
{
    private readonly IProductRepository _repository;   // a Domain port (just an interface)
    private readonly CatalogMapper _mapper;

    public ProductService(IProductRepository repository, CatalogMapper mapper)
    {
        _repository = repository;
        _mapper = mapper;
    }

    public async Task<IReadOnlyList<ProductDto>> GetAllAsync(CancellationToken ct = default)
        => _mapper.ToDtoList(await _repository.GetAllAsync(ct));
}

What's happening here: ProductService says “give me something that can do IProductRepository” in its constructor. It never mentions a database, EF Core, or a concrete class. It cannot — Application doesn't reference Infrastructure at all.

Infrastructure provides the real implementation:

internal sealed class ProductRepository : IProductRepository
{
    private readonly CatalogDbContext _db;
    public ProductRepository(CatalogDbContext db) => _db = db;

    public async Task<IReadOnlyList<Product>> GetAllAsync(CancellationToken ct = default)
        => await _db.Products.AsNoTracking().OrderBy(p => p.Id).ToListAsync(ct);
}

What's happening here: ProductRepository is the real thing that touches the database. It implements the same IProductRepository the service asked for.

Analogy. Application fills out an order form (IProductRepository) — “I need a repository.” Infrastructure is the warehouse that actually ships the item — “I am the real repository.” Application never visits the warehouse; it just hands over the order form.
In simple words: at runtime the request flows down through Application into Infrastructure — but Application only ever talks to an interface, so it stays clean and testable.

2 · The compile-time / project-reference flow

A different question: which .csproj references which? This is about building, not running.

Api→ Infrastructure→ Application→ Domain

This feels backwards — you'd expect the Api to reference Application (it uses the service!). The reason is that Infrastructure contains the module's registration code, and the host needs it. Here is the real registration:

public sealed class CatalogModule : IModule
{
    public IServiceCollection Register(IServiceCollection services, IConfiguration configuration)
    {
        services.AddDbContext<CatalogDbContext>(options =>
            options.UseNpgsql(configuration.GetConnectionString("Postgres")));

        services.AddSingleton<CatalogMapper>();
        services.AddScoped<IProductRepository, ProductRepository>();
        services.AddScoped<IProductService, ProductService>();
        services.AddScoped<ICatalogModule, CatalogModuleApi>();
        return services;
    }
}

And the host calls it indirectly at startup:

// Kheprx.BaseBackend.Api/Program.cs
builder.Services.AddModules(builder.Configuration);   // finds every IModule and calls Register(...)

What's happening here: AddModules discovers each IModule (like CatalogModule) and runs its Register. Because CatalogModule lives in Infrastructure, the host must reference Infrastructure to reach it. Notice the host does not reference Application directly — it comes in transitively (Infrastructure already references Application), which is why the controller can still see IProductService.

In simple words: the host references Infrastructure because that's where the “wiring sheet” (Register) lives. Application tags along for free through Infrastructure.

The key difference

Runtime flow — who calls whom

API → Application → Infrastructure → Database

Project references — who builds against whom

API → Infrastructure → Application → Domain

They are not the same diagram. The reference graph on the Architecture page draws the second; the Request Flow page draws the first.

Why the API references Infrastructure

Because the Host/Api is the composition root — where every module's registrations come together and the container is built. Think of it as the electrician who, at startup, wires every plug (interface) to the right socket (implementation) so the appliances just work. Here is what the container does:

  1. At startup, Register records the bindings: IProductService → ProductService and IProductRepository → ProductRepository.
  2. A request arrives. The container needs a ProductsController; it sees the constructor wants IProductService.
  3. It looks up the binding and builds a ProductService.
  4. ProductService's constructor wants IProductRepository; the container builds a ProductRepository.
  5. ProductRepository wants a CatalogDbContext; the container builds that too, then hands the finished controller back to ASP.NET.
In simple words: nobody calls new. The host wires interfaces to implementations once, and the container assembles the whole chain for you on every request.

The expert rule

The controller should depend on an Application abstraction, never on a concrete database type:

private readonly IProductService _service; // ✓ depend on the Application interface
private readonly CatalogDbContext _db; // ✗ never inject the DbContext into a controller
private readonly ProductRepository _repository; // ✗ not preferred — a concrete Infrastructure type

The real controller follows the rule exactly:

public sealed class ProductsController : BaseApiController
{
    private readonly IProductService _service;
    public ProductsController(IProductService service) => _service = service;

    [HttpGet]
    public async Task<ActionResult<ApiResponse<IReadOnlyList<ProductDto>>>> GetAll(CancellationToken ct)
        => Ok(ApiResponse<IReadOnlyList<ProductDto>>.Success(
            "Products retrieved", await _service.GetAllAsync(ct)));
}

Simple mental model

  1. API calls Application. The controller uses IProductService.
  2. Application asks for an interface. The service uses IProductRepository (a Domain port).
  3. Infrastructure implements the interface. ProductRepository is the real implementation.
  4. DI connects them at startup. The host (composition root) wires it all together.
